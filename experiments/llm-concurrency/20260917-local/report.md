# 本地 LLM 并发测试记录

2026-09-17 09:56 北京时间启动。使用项目 `.venv` 和 `.env` 配置，从本机调用真实 DeepSeek API。

**在本次固定输入重放测试中，4 路并发将四个角色全部完成的中位耗时从 7.92 秒降至 2.64 秒，约快 3 倍；单次回复没有变快，发言也没有明显变长。此次没有复现平均等待一分钟的现象。**

## 对比结果

每批包含四个角色请求；各并发度重复三批，正式测量共 36 个任务。另有四个预热任务，预热中发生一次重试，总计 41 次真实 HTTP 请求。

| 第一位角色完成，中位耗时 | 2.381 秒 | 2.581 秒 | 2.588 秒 |

正式测量的单任务耗时范围为 1.243–2.878 秒，平均 2.045 秒。发言长度为 44–79 个字符，平均 58.75 个字符，字符数包含标点和英文姓名。

三种并发度下的单次延迟差异很小，样本量不足以判断轻微差异是否稳定。可以确认的是，同一批独立工作并行完成时，总等待明显下降；第一个角色的结果并没有更早出现。

## 测试配置与方法

| 配置 | 实际值 |
| --- | --- |
| API 地址 | `https://api.deepseek.com` |
| 配置的模型名 | `deepseek-v4-flash` |
| 所有响应返回的模型名 | `deepseek-flash` |
| 思考模式 | `disabled` |
| JSON 模式 | 开启 |
| 输出上限 | 2400 tokens |
| HTTP 超时参数 | 60 秒；不是整个任务的绝对截止时间 |
| 额外重试上限 | 2 次 |
| 重试等待 | 2 秒，随后 4 秒 |
| 响应方式 | 非流式；计时包含完整响应读取、解析和现有校验 |

四个测试输入来自合法的首轮游戏快照，覆盖两份普通角色完整策略协议和两份邪恶角色表演协议。先前发言是测试脚本明确安排的公开台词，通过游戏引擎产生事件；并非另一个测量任务生成的回答。每个快照中的发言人、资源余额、队伍及合法行动均来自当时的游戏状态。

每个任务使用独立复制的游戏、角色记忆与策略管理器，直接调用生产代码中的 `Agent.prepare()` 和 `ChatClient.complete()`。返回计划先经原有校验，然后在该任务独有的游戏副本上执行 `Game.act()`，核查实际行动合法性。没有在真实对局中同时推进多个角色。

预热四个角色后，正式批次顺序为：

1. 第一轮：1 路 → 2 路 → 4 路。
2. 第二轮：2 路 → 4 路 → 1 路。
3. 第三轮：4 路 → 1 路 → 2 路。

同一个角色在各组的首次请求体 SHA-256 完全一致，覆盖模型参数、完整 system prompt 和游戏上下文。由任务起止时间检查到的实际并发峰值分别为 1、2、4，均未超过设定值。请求头时间只作为辅助记录，**不能当作首 token 时间**，因为服务可能先发送 HTTP 头和保活内容。

首轮输入 token 数按角色为 4833、4476、4847、5629。普通角色 system prompt 为 11289 字符，邪恶角色为 9301 字符。重复输入使正式测量的缓存命中率达到 95.10%；预热请求也已有部分缓存命中，因此预热结果不能视为完全冷缓存测试。

## 重试和输出观察

预热的 P5 第一次响应耗时 9.510 秒，返回 `finish_reason=stop`、1584 个输出 tokens，但解析阶段报 `invalid_response`。等待 2 秒后重试成功，第二次请求耗时 2.713 秒，输出 529 tokens；该任务总耗时 14.228 秒。

失败原文没有保存，因此这里不进一步推断是哪一种 JSON 或响应结构问题。其余正式测量任务均一次通过，没有观察到超时、限流或最终失败。

| 正式测量中的协议 | 任务数 | 平均任务耗时 | 平均输出 tokens |
| --- | ---: | ---: | ---: |
| 普通角色完整策略（policy） | 18 | 2.551 秒 | 523.6 |
| 邪恶角色表演（performance） | 18 | 1.539 秒 | 134.7 |

普通角色生成的机器字段更多，观测到的输出量与耗时也更大。这是两类请求的观察对比，不是只改变输出结构的因果实验。

36 个正式任务中，24 个选择 SOCIAL，12 个选择 PASS。当前协议即使选择 PASS 仍须生成 social 字段，所以统计中的发言长度包含这些未被行动发布的候选台词；逐条记录有 `speech_published_by_action` 可区分。生成内容不等于图形界面实际展示的发言。

现有格式、引用、隐私及行动校验全部通过。额外的游戏身份／现代技术用语关键词检查没有命中；这只是一项有限的检查，不能证明每条回答都满足世界观、人物动机、事实准确性或对前文的回应要求。并发组之间没有进行盲评，不能据此声称质量提高。

## 结果的适用范围

- 这是相同输入的重放吞吐测试。它验证了独立请求的并发收益，**不等于将实时轮流发言直接改为并发后仍能保持相同对话质量**。
- 没有测试“并发预分析＋顺序最终发言”两阶段方案，也没有测试备用请求竞速；这些方案可能增加调用量，应单独测量。
- 样本只有首轮四种角色上下文、每模式三批，且缓存命中率高。结果不能推广到后期长历史、完全冷缓存、其他模型或其他服务负载时段。
- 没有计入用户阅读、Godot 界面刷新、后端排队或完整对局的等待。此次没有复现一分钟延迟，也就不能认定并发已经修复了该问题。
- 并发没有解除 240 字符限制，也没有改变短句提示词。输出短和角色表现问题仍需单独调整协议并评估。

当前结果支持在相互独立的准备工作中使用并发。对于实时对话，应保留按最新事件作出最终决策的步骤；下一次若出现一分钟等待，应在实际游戏调用链中记录请求耗时和重试原因，与本记录对照。

## 数据与复现

- `metadata.json`：运行配置、每份上下文及 system prompt 的长度与哈希。
- `requests.jsonl`：40 个任务，内含 41 次尝试的耗时、usage、校验结果及已通过检查的公开文本。
- `batches.jsonl`：10 批计时，包含一批预热。
- `summary.json`：正式测量的分组汇总。
- `analysis.json`：加速比、输出统计、实际并发峰值及一致性检查。
- `source-manifest.json`：测试时相关源文件 SHA-256 及 Python 版本。
- `verification.json`：本地测试及数据一致性检查记录。

```

```
